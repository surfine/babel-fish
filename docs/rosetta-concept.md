# Rosetta：Slack 中英雙語閱讀與回覆

構思、設計與技術路線 · v0.1 · 2026-10-30

設計稿：[design/prototype.html](../design/prototype.html)（用瀏覽器打開，右上角「設計註解」會標出每個設計決定）

## 一句話

讀的時候，英文下面附台灣繁中；寫的時候，用中文起草，由模型改成這個頻道的人會寫的英文，你看過、親手按下送出才發。

## 要解決的三件事

1. **讀得懂語氣，不只讀懂字面。** 這個頻道是連發的短訊息、縮寫和內部用語（fwiw、fine print、Find My-esque），一般機翻常翻得字面正確但語氣全錯。
2. **寫得像這裡的人。** 文法正確不夠。這裡的人小寫開頭、不加句號、一個意思拆兩三則連發；一般翻譯會產出 “I also have the same situation.” 這種一看就是翻譯腔的句子。
3. **敢按送出。** 訊息是以你的名義發出去的。你需要一個不靠英文能力就能確認「意思沒變、沒多說、語氣沒加重」的方法。

## 現有工具做到哪裡

2026-10-30 查官方頁面的結果（未實測）：讀的一端已經有人做，寫的一端沒有工具會看頻道語境改寫，也沒有回譯核對。

| 工具 | 讀 | 寫 | 缺什麼 |
| --- | --- | --- | --- |
| Slack AI「Translate message」 | 逐則手動翻，譯文取代原文（只有自己看得到），下方可切回原文 | 沒有改寫你要送出的訊息；Slackbot 能幫你起草，但不是改寫你寫好的訊息 | 只有 Business+／Enterprise+ 方案；不是常駐雙語，也不並排 |
| Slack Marketplace 翻譯 App（Smart Translate、Translate Channels、Harmony 等） | 有的把譯文貼在原文下方，有的直接改所有人的訊息 | 無 | 要裝進 workspace；多半會讓別人也看到譯文 |
| 沉浸式翻譯 | 官方文件只寫 Discord 雙語，沒寫 Slack | 輸入框翻譯會直接取代文字，沒有審稿步驟 | 不看頻道語境、無回譯 |
| Grammarly／DeepL／Raycast | 選取翻譯 | 能潤英文、能翻中轉英；Raycast 可設定先預覽再貼回 | 不知道這個頻道怎麼說話；無回譯核對 |
| Apple 系統翻譯與 Writing Tools（macOS 27） | 選取文字翻譯，第三方 App 支援不穩 | Rewrite 不做中轉英 | 同上 |

值得借的模式：譯文只有自己看得到並可切回原文（Slack AI）、譯文貼在原文正下方（Smart Translate）、先在面板裡審再貼回而不是原地取代（Raycast）。Reddit 的教訓是譯文標示要夠醒目，有使用者沒發現自己在看機翻。

## 發散：六種產品形態

| 形態 | 長相 | 好處 | 代價 |
| --- | --- | --- | --- |
| A. 瀏覽器擴充套件 | 疊在 Slack 網頁版上：每則訊息下方插入譯文，輸入框上方加 Rosetta 審閱卡 | 不用 workspace 管理員同意；Slack 原有功能全部保留；開發最快 | 要改用瀏覽器開 Slack；Slack 改版 DOM 就要跟著修 |
| B. 獨立客戶端 | 自己做一個 Slack 客戶端（Tauri／SwiftUI），雙語是原生設計 | 介面完全自由，可以做雙欄對照、整段摘要 | 要重做討論串、表情回應、檔案、未讀、通知等大量功能；需要 Slack API 權杖 |
| C. Slack 內的 App | 在 Slack 裡用捷徑或 AI agent 窗格呼叫 Rosetta；agent 能知道你正在看哪個頻道 | 留在 Slack 桌面版裡用 | 要裝進 workspace（預設成員可自己裝，但 Owner 若開了 App 核准就得申請）；agent 預設以 bot 身分發言，要以你的名義送出得另外取得使用者權杖；做不到常駐雙語 |
| D. 桌面伴侶視窗 | Slack 旁邊一個窄窗，鏡像目前頻道的雙語版本，下方是中文輸入與審閱 | Slack 桌面版照常用 | 兩個視窗切換；讀取仍需 API 權杖 |
| E. 全系統快捷鍵 | 任何 App 選取文字按快捷鍵：英文 → 中文浮窗；中文 → 審閱卡 → 貼回 | 半天可做出來，Slack、郵件、iMessage 都能用 | 沒有常駐雙語，每次都要手動選取 |
| F. 改裝 Slack 桌面版 | 往 Slack 的 Electron 程式注入腳本 | 外觀上最理想 | 不可行：這台 Mac 上的 Slack 4.53.269 實查開了 ASAR 完整性檢查、只從 asar 載入、hardened runtime，改檔案會被直接終止，自動更新也會蓋掉 |

三種讀者面的取捨：A 和 B 能做到「整個頻道常駐雙語」；C、D、E 只能做到「需要時翻」。寫作面五種都做得到，差別只在送出的方式（直接 API 送出，或填進 Slack 輸入框由你按 Enter）。

## 設計稿裡的決定

核心互動不綁形態：同一套閱讀層和審閱卡，可以注入 Slack 網頁版（A），也可以是獨立客戶端（B）的原生介面。

**閱讀**

- 三種閱讀模式：「對照」（英文下附中文，預設）、「中文優先」（中文當正文，英文縮成一行灰字，點開看全文）、「英文練習」（只看原文，點一下才出譯文）。每個頻道各自記住。
- 譯文用細直線和不同字色標示，任何時候都分得出哪些字是機器產生的。
- 俚語、縮寫、片語用點狀底線標出，滑過看意思和用法。地道的寫法是從讀別人怎麼說累積來的。
- 離開一段時間回來，先給一段中文摘要。
- 術語表：Find My 譯成「尋找」，AirPods Pro、iPadOS 27 這類保留原文。翻譯與潤色共用同一張表。

**寫作**

- 用中文寫，⌘↩ 才潤色。中文輸入法用 Enter 選字，所以 Enter 只換行，不會選字選到一半就觸發。
- 潤色時帶入脈絡：最近 20 則對話，加上你指定要回應的那則（滑過訊息按「回覆這則」）。代名詞、省略句才翻得對。
- 審閱卡在輸入框上方展開，不是彈窗，看得到上面的對話：
  - 會送出的英文可以直接改。頻道習慣連發，預設拆成兩則，一鍵合併。
  - 語氣三段：更隨意／像這個頻道（預設）／更正式。
  - **回譯**：把英文翻回中文給你核對。多了你沒說的話（例如模型自己加了 “report back”）或語氣說重了（「也許」變成 prob），用黃色標出並寫明差在哪。
  - 「為什麼這樣寫」：每個關鍵用字一句解釋，順便學。
  - 「再調整」：打一句「短一點」「熱情一點」就重寫。
- 送出保護：送出永遠要親手按；審閱卡剛出現的 0.8 秒內按鈕不作用，避免連按 ⌘↩ 誤送；送出後有 5 秒撤回。
- 自己送出的訊息下方顯示你的中文原稿，而不是機器回譯。

## 「地道」怎麼做出來

這是整個工具的品質核心，靠的不是換更大的模型，而是給模型對的材料和檢查：

1. **頻道語氣檔案**：用程式（不用模型）統計最近 200 則訊息的小寫開頭比例、句尾標點、常見縮寫、平均長度、連發習慣，再挑 10–20 則真實訊息當範例。潤色時把統計和範例一起給模型。
2. **你自己的英文聲音**：如果你過去在 Slack 寫過英文，拿來當範例，潤色結果會像你，而不是像別人。
3. **反翻譯腔清單**：不用破折號、不加 “Great point!”、不過度客氣、不灌驚嘆號、不把隨意的話寫成完整句子。
4. **獨立回譯**：回譯由另一次呼叫完成，而且**不給它看你的中文原稿**；否則模型會直接抄原稿，檢查就失效了。之後再拿回譯和原稿比對，列出新增、遺漏、語氣強弱差異。
5. **結構化輸出**：潤色結果用固定 JSON 回傳（訊息陣列、合併版、說明），介面才能穩定地畫出審閱卡。
6. **評估集**：把你實際寫過的中文草稿和最後送出的英文存下來（只存本機），之後換模型或改提示詞時拿來比對品質。

## 技術路線

### 建議：先做瀏覽器擴充套件（形態 A），把 Slack 網頁版裝成獨立視窗用

理由按重要性排：

1. **不用任何人同意。** 擴充套件只是讀你自己瀏覽器裡已登入的頁面，和沉浸式翻譯、Grammarly 同一類。走 Slack API（B、C、D）就得在工作的 workspace 建一個 App：成員預設可以自己裝，但只要 Workspace Owner 開了 App 核准，就變成送申請等管理員審權限；而且一用 API，就適用 Slack 的開發者政策，其中「不得與第三方分享資料」一條沒說明送去 LLM 翻譯算不算。
2. **Slack 原有功能全部保留。** 討論串、表情回應、檔案、通知、未讀、huddle 都不用重做；獨立客戶端（B）光是補齊這些就是好幾個月的工作。
3. **最快驗證核心價值。** 這個工具成敗在「英文夠不夠地道」，不在外殼。先用最便宜的外殼把潤色品質做到位。
4. **體驗差距可以縮小。** Chrome 有「將網頁安裝為應用程式」，理想上 app.slack.com 會變成沒有網址列的獨立視窗，擴充套件照常運作。但有報導指出 Slack 網頁版在 Google 的新筆電上被判定為不合規的 PWA，只能開成分頁；macOS 的 Chrome／Edge 會怎樣要實測，最差情況是開一個專用的 Chrome 視窗。

要接受的代價：改用網頁版取代 Slack 桌面版；Slack 改版時 DOM 選擇器要跟著修（把選擇器集中在一個檔案、加上冒煙測試，壞了一眼看得出來）。

### 架構

```
Slack 網頁版（app.slack.com）
 ├─ content script ── 解析畫面上的訊息（MutationObserver），在每則下方插入譯文
 │                   在輸入框上方掛 Rosetta 輸入區與審閱卡（Shadow DOM，樣式不互相污染）
 │                   你按送出 → 等 5 秒撤回期 → 把英文填進 Slack 輸入框並送出
 └─ background service worker
      ├─ 翻譯佇列：把畫面上新出現的訊息批次送翻（每批 10–20 則，附前文與術語表）
      ├─ Claude API（金鑰存在本機擴充套件儲存區）
      └─ IndexedDB：譯文快取（以頻道 + 訊息 ts + 內文雜湊為鍵）、語氣檔案、術語表、評估集
```

| 環節 | 選擇 | 說明 |
| --- | --- | --- |
| 擴充套件框架 | WXT + TypeScript | Vite 建置、熱更新、Manifest V3 |
| 注入的介面 | Preact（或原生 Web Components）+ Shadow DOM | 體積小，不受 Slack 樣式影響 |
| 模型呼叫 | 官方 `@anthropic-ai/sdk` | 在 service worker 直接呼叫，不需要自己的伺服器 |
| 本機資料 | IndexedDB | 譯文只存在這台電腦 |

送出這一步刻意做成「填進 Slack 自己的輸入框再按 Slack 的送出」，而不是另外打 API：訊息和你手打的一模一樣，沒有「由某 App 傳送」標記，也不需要任何權杖。撤回期是在 Rosetta 這邊先扣住 5 秒，真的還沒送到 Slack。

### 每一步用哪個模型

| 工作 | 模型 | 理由 |
| --- | --- | --- |
| 逐則翻譯、俚語標註 | Claude Haiku 5.5 | 量大、要快、便宜；術語表和頻道說明放在可快取的前綴 |
| 未讀摘要 | Claude Haiku 5.5，必要時 Sonnet 5.5 | 一段中文摘要 |
| 潤色（一次產出隨意／頻道／正式三種語氣） | Claude Opus 5.5（effort low–medium）或 Sonnet 5.5，M0 實驗後定 | 品質核心；三種語氣一次產出，切換語氣不必再等 |
| 獨立回譯 | Claude Haiku 5.5 | 只給英文，不給中文原稿 |
| 意思比對（新增、遺漏、語氣強弱） | Claude Sonnet 5.5 | 需要判斷力，輸入很短 |

| 項目 | 假設用量 | 每月約 |
| --- | --- | --- |
| 閱讀翻譯（Haiku 5.5：每百萬 token 輸入 $0.10／輸出 $0.50） | 每天 200 則 | 不到 US$2 |

### 備案

- **如果你一定要留在 Slack 桌面版**：先做形態 E（全系統快捷鍵，選中文 → 審閱卡 → 貼回），寫作端可以完全沿用同一套潤色與回譯流程；閱讀端則退化成選取翻譯。
- **如果 workspace 允許你裝 App**：之後可以加一條 Slack API 管道（使用者權杖 + Socket Mode，私人頻道用 `groups:history` 收 `message.groups` 事件），讓語氣檔案、你的歷史英文訊息、討論串脈絡改從 API 拿，比解析畫面可靠。只裝在這個 workspace 的內部 App 不受 2025-05 那次 `conversations.history` 降速影響。再往後才考慮獨立客戶端（B）。
- **不做**：改裝 Slack 桌面版（F），也不借用網頁版的登入權杖（xoxc＋cookie）跑第三方客戶端。前者被完整性檢查擋住；後者有公開案例顯示權杖會被 Slack 偵測後作廢，slackdump 也警告可能觸發安全警示並通知管理員。

### 資料與責任

- 私人頻道的內容會送到 LLM API 翻譯。商業 API 通常預設不拿輸入訓練模型，但這是公司的內部頻道，**是否可以外送該由你（或你的公司）決定**，這是開工前唯一真正的阻擋點。
- 譯文、草稿、評估集只存在本機。API 金鑰存在擴充套件的本機儲存區，不進任何雲端。
- 每則訊息都要你親手按送出；沒有自動回覆、沒有排程送出。

## 分階段計畫

| 階段 | 內容 | 完成判準 |
| --- | --- | --- |
| M0 品質實驗台（1–2 天） | 一支本機小工具：貼上頻道最近 20 則 + 你的中文草稿 → 潤色、獨立回譯、意思比對；同一批草稿比較 Opus 5.5 與 Sonnet 5.5 | 用你的 15–20 則真實草稿，你覺得「可以直接送」的比例夠高；定下模型、提示詞和評估集 |
| M1 閱讀層 | 擴充套件解析訊息、批次翻譯、快取、三種閱讀模式、俚語註解、術語表 | 在主要工作頻道捲動流暢，譯文延遲 2 秒內出現，重開不重翻 |
| M2 寫作層 | Rosetta 輸入區、審閱卡、回譯警示、拆則、5 秒撤回、填入 Slack 送出（Slack 輸入框的實作要先實測：用 `insertText` 或模擬貼上） | 從中文草稿到送出全程不碰英文輸入框；連按 ⌘↩ 不會誤送 |
| M3 打磨 | 頻道語氣檔案、你的英文聲音、未讀摘要、用量顯示 | 語氣檔案每天自動更新；評估集分數不退步 |

M0 放在最前面，是因為「夠不夠地道」是整件事最大的未知數；介面已經在設計稿裡驗證過，風險低。
